# Audit — 2026-08-08

Cross-repo engineering audit of the Mon toolchain, recorded per repo. Every finding here was
reproduced against the code before it was written down.

Audited state: `main`, working tree clean, 22 tracked files, 9 tests passing in 12.7s.

The summary: **decent software hygiene wrapped around unsound methodology.** The package layout,
the shared normalisation path and the hybrid detection design are all right. The published accuracy
number and the label logic are not.

## Critical

### C1 — ASCII digits, punctuation and spaces are counted as Latin script

**Location:** `src/mon_language_detector/detector.py:83`, used at `:88-92`

**Evidence.**

```python
latin = sum(1 for c in cleaned if "\u0000" <= c <= "\u024F") / total
```

`U+0000-U+024F` includes the space, every ASCII digit, and every ASCII punctuation mark. Run against
the committed `.ftz`:

```
digits only   ->  eng      confidence=1.0        reliable=True
punct only    ->  eng      confidence=1.0        reliable=True
Mon + year    ->  mnw-eng  confidence=1.0000088  reliable=True
pure Mon      ->  mnw      confidence=1.0000098  reliable=True
```

**Reasoning.** `1234567890` and `!!! ,,, ???` contain no letters in any script, and both are returned
as English at full confidence with `reliable=True`. Mon text whose only non-Myanmar content is a
Western year is returned as code-switched.

`utils.py:44` compounds it: normalisation handles `\n` and `\t` only, so U+00A0 NBSP survives and
counts as Latin.

**Impact.** The stated purpose is corpus filtering (`README.md:3`). Every numeric table row and
citation block in a scrape is confidently filed as English, and any Mon line carrying a date or
percentage becomes `mnw-eng`. Both corrupt a downstream corpus silently, and `reliable=True` means a
caller filtering on that flag has no defence.

**Fix.** Restrict the range to actual Latin letters and exclude `Zs`/`Nd`/`P` categories from the
denominator. Then add roughly thirty labelled strings run against the real model — the current suite
would not have caught this.

**Confidence:** high. Reproduced directly.

### C2 — Train/valid leakage by construction; the published accuracy is unmeasurable

**Location:** `src/mon_language_detector/pipeline.py:47-49` and `:111-113`

**Evidence.**

```python
if 0 < len(lines) < target:              # :47-49
    factor = (target // len(lines)) + 1
    lines = (lines * factor)[:target]
...
random.shuffle(dataset)                   # :111
split = int(len(dataset) * 0.9)           # :113
```

**Reasoning.** Lines are upsampled by duplication and only then shuffled and split 90/10, so exact
duplicates land on both sides. Default targets are 1,000,000 per language; Mon is the language most
certain to fall short and therefore the most duplicated. `_extract_lines` performs no deduplication,
so naturally occurring duplicates straddle the split too, and `_make_mixed` (`:72`) builds synthetic
samples from lines already in the dataset.

There is no `random.seed()` anywhere in the file, and `train.py:100` never passes fastText's `seed`.

**Impact.** `README.md:26` publishes **Precision@1 0.925**, measured by `train.py:55` on that
contaminated file. Its true value is unknown, and it cannot be reproduced to find out.

**Fix.** Deduplicate before splitting, or split first and upsample only the train side. Seed every
RNG.

**Confidence:** high. Read directly from the source; no seeding call exists in the file.

## High

### H1 — `confidence` silently changes units

`detector.py:92` assigns a script ratio to `conf`; `:60` and `:95` assign hardcoded literals (0.95,
0.85); the model posterior is used elsewhere. `:100` then thresholds all of them against 0.80 as
though they were one quantity.

The confidences above 1.0 in C1's output are the proof: a probability cannot exceed 1, so that field
is demonstrably not always a probability. `reliable` is therefore not a calibrated guard, and a
caller cannot threshold on `confidence`.

### H2 — The built wheel contains no model

`utils.py:7` resolves `PROJECT_ROOT = Path(__file__).resolve().parent.parent.parent`, and
`detector.py:43` looks for the `.ftz` under it. The 7.4 MB model lives at the repo root, outside the
package directory, with no package-data configuration — a built wheel contains only the `.py` files.

It works today only because `uv sync` installs the project editable, so `PROJECT_ROOT` resolves back
to the repo. In a real install it becomes `<venv>/lib/python3.11` and `detector.py:45` raises
`FileNotFoundError`.

`README.md:56-62` documents a Python SDK, and `py.typed`, `[build-system]` and `[project.scripts]`
all signal distribution intent. None of it survives packaging.

**Fix.** Move the `.ftz` into `src/mon_language_detector/data/` and resolve via
`importlib.resources`.

### H3 — Nine tests, none of which test classification

`tests/test_detector.py:5-19` defines a two-line `DummyModel` returning 0.99, and monkeypatches
`fasttext.load_model` to return it. Of the 9 passing tests, 4 use that stub, 3 test string utilities
and 2 test CSV/TSV I/O. **No test loads the committed `.ftz`.** Every bug in C1 and H1 lives in code
the suite exercises against a stub that cannot fail.

The monkeypatch at `:12` is never restored (only `Path.exists` is, at `:19`), so it leaks into any
later test in the session.

## Medium

- **No held-out test set.** The pipeline emits only `train.txt` and `valid.txt`, and `valid` is used
  for the in-training report, the post-quantisation report, and the README number. Any tuning done
  against that number is selection on the reported set.
- **Burmese donor words injected into Mon sentences, labelled `mnw`** (`pipeline.py:63, 75-76`).
  Half the synthetic mixed samples insert a Burmese token into a Mon sentence and label the result
  Mon. mnw-vs-mya is this classifier's hardest boundary — both use Myanmar script — so this teaches
  the model that Burmese n-grams are Mon evidence. Whether it is net-harmful needs an ablation; it is
  currently unmeasured.
- **Train/serve length mismatch.** `_extract_lines` drops anything ≤10 characters, so the model never
  trains on short input, while `detector.py:74` sends anything ≥3 characters to `predict`.

## Low

- The 7.4 MB `.ftz` is committed directly to git with no checksum and no record of which corpus or
  commit produced it. Every retrain adds another 7.4 MB permanently.
- `detector.py:12` documents a `mixed` label no code path produces; `:99` says the threshold is 20
  characters while `:100` uses 10.
- `uvx ruff check .` reports 41 findings, 33 auto-fixable. No lint or type configuration exists.

---

## What is good, specifically

- **The hybrid design is the right instinct.** Using a Mon-exclusive codepoint regex
  (`detector.py:32-39`) as a hard signal that can override the neural model (`:93-95`) is exactly how
  to handle a language sharing its script with a much higher-resource neighbour. The ranges are
  correct and annotated.
- **Returning `mnw-mya` for short ambiguous Myanmar text** (`:62-70`) is intellectually honest. Most
  implementations would guess or return `unknown`.
- **One normalisation path shared between training and serving.** `clean_and_normalize` is called
  from `pipeline.py:17`, `wrangle.py:30` and `detector.py:51`. Train/serve skew is the most common ML
  plumbing bug and this repo does not have it.
- Correct `src/` layout with `py.typed`, four clean CLI entry points, and a suite that runs in 12.7s.

## Roadmap

**Immediate.** C1 then C2. C1 is hours of work and is the highest-return change in the toolchain.
C2 invalidates the published 0.925, so it needs deciding whether to retrain and republish or to
withdraw the number until it can be measured.

**Next.** H2 (move the model into the package), then H3 — roughly thirty labelled strings against
the real `.ftz`, which would have caught C1 immediately.

**Long-term.** A held-out test set, and an ablation on the Burmese-donor augmentation.
